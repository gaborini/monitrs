# The road to 1.0.0, and the feature set after it

**Date:** 2026-07-31 · **Status:** approved, not started · **Current version:** 0.2.0 (pre-release)

This document defines what `1.0.0` means for monitrs, the four work streams that get it
there, and the three features that land in `1.1.0` afterwards. It exists because `0.2.0`
is marked a pre-release for reasons that are written down rather than felt, and closing
those reasons is a different kind of work from adding features — worth separating on
purpose.

Every measurement quoted here comes from `docs/benchmarks.md` or `CHANGELOG.md`. Where a
number is not measured, this document says so instead of estimating.

**Two conventions.** A bare `§n` is a section of the local development specification, the
same as in the code comments; a reference to this document says so ("§2 of this document").
And the implementation plan derived from here covers streams A–D and the release only —
each `1.1.0` feature in §8 gets its own design document before any of it is built.

## 1. What 1.0.0 is

**A stability promise, not a feature milestone.** SemVer's `1.0.0` says "the surface you
build against will not break under you without a major bump". It does not say "feature
complete", and monitrs should not pretend otherwise.

The release contains exactly four things:

| Stream | What it closes |
|---|---|
| **A** | The idle self-CPU p95 budget, which §16.1 sets and `0.2.0` misses |
| **B** | The freeze, enforced by CI rather than by good intentions |
| **C** | The spec backlog — what the specification already promises but the interface does not show |
| **D** | The validation the pre-release flag is standing in for: the soak, real Linux, the published archives |

What the release freezes:

* the **library API** of `monitrs-core`, `monitrs-collectors` and `monitrs-tui`;
* the **JSON export schema**, at `schema_version = 2`;
* the **configuration keys** and their meanings;
* the **default keymap** — a binding may be added, but an existing one does not change
  meaning without a major bump.

## 2. What 1.0.0 is not

* **No new metric and no new screen.** The three features chosen from the competitive
  review (§8 of this document) land in `1.1.0`, on a branch that merges after the tag.
  Stream C is not an exception to this: it surfaces values the core already computes and
  §2.5 already promises, and adds no reading the collector was not taking.
* **No change to the §3.2 non-goals.** No Windows, no daemon, no eBPF, no per-process
  bandwidth, no GPU in the default build, no plugins, no history persisted across
  launches. These stay non-goals through 1.x; `1.0.0` does not quietly relax them.
* **Not a promise about appearance.** Layouts, wording, colours and glyph choices are
  presentation, not API, and the CHANGELOG must say so explicitly — otherwise the first
  cosmetic improvement reads as a breaking change to somebody.

## 3. Stream A — close the idle self-CPU p95

### The measured situation

`docs/benchmarks.md` reports idle self-CPU median **0.5–1.1%** against a 1% budget —
met — and p95 **6–11%** against 2% — failed. The cause is located rather than guessed:
`sysinfo`'s `Components::refresh` costs about **85 ms** and runs on the 5-second medium
tier (`crates/monitrs-collectors/src/common/collector.rs:187`). Averaged, that is 1.7%
of a core; sampled once a second, the spike lands in one sample in five, which puts it
above the 95th percentile by arithmetic rather than by accident.

Two things are worth knowing before choosing a fix:

* **Measuring on §16.1's reference workload does not rescue it.** The 85 ms is not
  process-count dependent, and on an 8-CPU reference machine the same spike is a larger
  fraction of a core than on the 12-core host the current figures come from.
* **Moving the read to a background thread does not rescue it either.** Self-CPU is
  process CPU. Relocating the work does not reduce it.

### A1 — measure whether the read itself can be cheaper (first, because it may be enough)

`Components::refresh(true)` rebuilds the component list as well as reading it. Newer
`sysinfo` versions expose per-component refresh. Measure, in this order:

1. `refresh(false)` versus `refresh(true)` — is the list rebuild a material part of the 85 ms?
2. refreshing **one** component (the sensor behind the header's hottest reading) versus all of them.

If a single-component read is cheap, the budget is met by a change of a few lines and
A2 becomes an ergonomic improvement rather than a gate. This is measured first precisely
because it is the cheapest possible outcome.

**Constraint:** whatever this finds, §9.3 stands. No private or undocumented macOS API in
the default build, and no external command (`powermetrics`, `system_profiler`) in the
refresh loop. If the only cheaper path is an undocumented SMC key, the answer is no, and
A2 carries the stream alone.

### A2 — the sensor tier becomes demand-driven

Sensors come off the fixed 5-second medium tier:

* **Nobody is looking at a sensor:** the read runs on the **slow tier (30 s)**. The
  header's hottest-sensor segment (`crates/monitrs-tui/src/views/mod.rs:551`) and the
  compact summary line (`:755`) render the retained value **marked stale with its age**,
  which the interface already does for every retained metric. This is not a compromise
  in precision but an increase in it: the header's single number is a glance, and the
  Battery screen is the instrument.
* **The Battery screen is opened:** entering the screen emits an on-demand refresh, and
  while it is the visible screen the sensor read returns to the medium (5 s) cadence.

The mechanism already exists and is not new architecture: `Effect::FetchProcessDetail`
(`crates/monitrs-tui/src/action.rs:740`) puts work on the on-demand worker, and
`Effect::RequestSample` (`:738`) asks the sampler for a sample now. Screen entry emitting
an effect is the established pattern; the collector gains an interest flag for sensors
rather than a new scheduling concept.

**Boundaries this must respect:**

* A sensor value that has never been read is `warming up`, not `0`, and not absent.
* A retained value shows its age. A 30-second-old temperature is honest; an undated one
  is not.
* A machine with no sensors keeps saying so once, in the panel label — the demand-driven
  path must not turn "unsupported" into "warming up" forever.

### A3 — publish both numbers

While the Battery screen is open, the 5-second cadence returns and the p95 spike returns
with it. That is the price of the reading the user asked for, and it gets published rather
than avoided: `docs/benchmarks.md` gains two rows, **idle** and **Battery screen open**,
each with the workload stated. §16.1's budget is about idle self-CPU, so the gate is met
by the idle row; the second row exists so nobody discovers it themselves and concludes
the first was a selective quotation.

### Rejected

* **Reinterpreting the instrument without changing the code** — publishing the average
  core share (1.7%) and demoting the p95 to informational. Defensible on the merits, but
  it is moving the goalpost, and this project's habit is to move the code.
* **Dropping macOS temperatures from the default build.** The reading is real and useful;
  the cost of *how often* it is taken is the actual problem.

### Testing

* A collector-level test that the sensor read is not issued on a fast tick, is issued on
  the slow tier, and is issued once on demand when the interest flag is set.
* A reducer test that entering and leaving the Battery screen sets and clears the interest.
* A snapshot test of the header with a stale sensor reading, asserting the age is rendered.
* A benchmark run recorded in `docs/benchmarks.md` for both rows of A3.

## 4. Stream B — enforce the freeze in CI

### B1 — the JSON schema field-path inventory

The README promises that `schema_version` is bumped "whenever a field is **removed** or
its meaning changes". Today nothing checks it.

Add a committed inventory, `docs/schema/v2.json`, listing every field path the version-2
export contains. A test exports a snapshot through the **fake collector** — deterministic,
already used by the test suite — walks the result, and compares path sets:

* a path in the inventory that the export no longer produces **fails the test**;
* a path in the export that the inventory does not list **passes**, because adding a field
  is not a break under the promise as written;
* the failure message names the missing path and says what the fix is: restore the field,
  or bump `schema_version` and write a new inventory beside the old one.

The old inventory files stay in the repository. `v2.json` remaining readable after `v3`
exists is what lets a consumer see exactly what changed.

### B2 — `cargo-semver-checks` in CI

A job that compares the workspace's public API against the last published version and
fails on a breaking change without a major bump. Chosen over `cargo-public-api` because it
runs on the stable channel `rust-toolchain.toml` already pins — `cargo-public-api` needs
nightly rustdoc JSON — and because its failures name the offending item rather than
presenting a diff to read.

The job is **advisory until the 1.0.0 tag** — there is nothing to be compatible with yet —
and **blocking from the first commit after it**.

### B3 — the policy, written down

`CONTRIBUTING.md` gains a short section stating:

* what is API and what is presentation (§1 and §2 of this document, condensed);
* that raising the MSRV is a minor bump, and that `Cargo.toml`'s `rust-version` is the
  record — `rust-toolchain.toml` pins the development channel, not the minimum;
* that a deprecation lives at least one minor cycle before removal;
* that `docs/schema/` is the export contract, and how to bump it.

### Testing

B1 *is* a test. B2 is a CI job. B3 gets a link from `README.md`'s development section so
it is discoverable from where people actually start.

## 5. Stream C — the spec backlog

### C1 — §2.5's comparisons reach the interface

`crates/monitrs-core/src/history/view.rs:311` already computes comparisons against the
previous sample and against 30 seconds ago (`ComparisonBaseline::THIRTY_SECONDS_AGO`), and
nothing in the interface uses them. §2.5 asks for exactly this, so the promise is
outstanding rather than optional.

Surface them on the **Time Lens caret**, which is where the third baseline §2.5 names — the
selected historical sample — already lives, and which today says only *when* the selected
sample is rather than *what changed*.

**A scope correction found while planning:** the comparison API is over `HistoryMetric`, the
system metrics, so this compares CPU against its baselines and not the selected process
against its own. Per-process comparison needs per-process history, which is §8.1's
`1.1.0` feature; promising it here would be promising a datum that is not retained.

States, not numbers, where a number would lie: a metric with no baseline yet is
`warming up`; a process that was not in the previous retained set is named as such rather
than shown as a change from zero; a refused metric stays `denied` on both sides of the
comparison.

### C2 — the tab strip below 92 columns

Seven screen names do not fit under 92 columns, which `0.2.0` introduced and its CHANGELOG
lists. Fix it with the existing priority-ordered fitting helper
(`crates/monitrs-tui/src/views/mod.rs:1130`, `join_fitting`): as room runs out the inactive
screens degrade to their digits, and **the active screen keeps its name** — losing the
label that says where you are is the one degradation that is not acceptable.

### Testing

Snapshot tests at 80, 92 and 160 columns, and a test that the active screen's name is
present in every one of them.

## 6. Stream D — validation

The pre-release flag stands for missing evidence. Each row below replaces a claim with a
record; nothing here is code.

| Gate | Where | Evidence produced |
|---|---|---|
| 12-hour soak, Linux | the physical Linux machine | RSS and descriptor curves per `docs/soak-testing.md`, no growth, nothing dropped |
| 12-hour soak, macOS | the development Mac, sleep inhibited | the same; 30 minutes is the only record today |
| Real Linux frames | the physical machine, then CI | `capture.rs` output committed as the Linux variants under `docs/screenshots/` |
| Battery screen on Linux | the physical machine, if it has a battery | today it is tested only from captured `/sys/class/power_supply` fixtures |
| The published archives | EC2 x86_64 + physical aarch64 | four of the six have never been executed; run `snapshot --format json` and a short interactive session from each |
| Nightly regression soak | CI, about 5 hours | not the gate — the net that keeps the 12-hour result from decaying unseen |

CI already runs the `#[ignore]`d platform smoke tests on `ubuntu-24.04` and macOS
(`.github/workflows/ci.yml:79`), so the Linux *collector* is exercised on every pull
request. What is missing is a rendered frame and an executed release binary, which is why
those two are named separately above.

**Protocol, so the numbers are comparable:** one workload description per run (host, core
count, process count, terminal size, sample interval, history span), the same
`docs/benchmarks.md` table shape, and the raw logs kept with the run. A soak that cannot
be quoted with its workload is not evidence.

## 7. Release mechanics

* `CHANGELOG.md` gains a `1.0.0` section whose **Known limitations** list is the honest
  remainder — including the A3 second row, and anything the soak surfaces.
* The `README.md` status block loses the pre-release paragraph and gains the freeze
  statement: what is API, what is presentation, and where the contract lives.
* `docs/release-checklist.md` gains the freeze steps (B1's inventory, B2's job flipping to
  blocking) so the next release cannot forget them.
* Tag `v1.0.0`, publish, and only then merge the feature branch.

## 8. After the tag: the 1.1.0 feature set

Chosen from a review of `htop`, `btop`, `bottom`, `glances`, `atop`, `ctop`, `nvtop`,
`zenith` and `procs` against monitrs' own principles. The selection rule was not "what do
they have" but "what does monitrs' existing data already almost answer".

### 8.1 Per-process Time Lens

btop draws a per-process graph; nobody lets you scrub one. monitrs already retains, per
sample, the top-K contributors per metric with stable identity and trend
(`crates/monitrs-core/src/history/contributors.rs:154`, over CPU, memory, disk read and
disk write), so the selected process's curve across the retained window is largely a
question of assembling what is stored.

The design work is not the drawing. It is the gap: **a process that fell out of the top-K
is not zero and is not interpolated.** The curve must render that interval as a named
absence, and the panel must say how much of the window the process was actually observed
in. Getting that wrong produces a chart that lies in the project's own house style, which
is worse than not shipping it.

### 8.2 Pressure event log

`diagnostics.bell_on_critical` rings, and nothing remembers. A bounded ring of escalations
— when, which signal, which rule fired, and the raw value that tripped it — answers "what
happened while I was not looking", which is the question monitrs exists for. The Pressure
Radar already renders the rule that produced a state, so this adds retention, not
measurement.

### 8.3 Panel zoom and column selection

`bottom`'s expanded widget and `htop`'s F2 setup, in monitrs' idiom: zoom the focused panel
to the full screen, and choose which columns the process table shows. Ergonomics rather
than new data — and the zoom relieves the same narrow-terminal pressure that C2 addresses.

Column selection is a **configuration key plus a palette command**, not an interactive
setup screen. The project is config-first with a palette as its second surface, a seventh
overlay is a cost, and a column set is exactly the kind of choice someone makes once and
wants to keep.

### Deferred, with the reason

* **Structured filter expressions** (`cpu>5`, `user=root`, `state=D`) — wanted, and the
  current text filter is its degenerate case, so it stays backwards compatible whenever it
  lands. Not in the first round by choice.
* **ndjson snapshot streaming**, **Linux I/O latency and queue depth**, **tagging several
  processes for one confirmed action** — all fit; all wait.
* **GPU** — Linux-only and feature-gated at best, because macOS exposes it solely through
  `IOReport`, which §9.3 forbids. An asymmetry this large needs its own design.
* **Persisted history and replay** (`atop`'s killer feature) — the closest thing to
  monitrs' identity in this whole list, and a §3.2 non-goal for v1. It needs an explicit
  design about what a recorded window is, not a quiet relaxation of a stated boundary.

### Where new work is specified

The development specification is local and gitignored, so new features cannot take § numbers
in a document nobody else can read. From `1.1.0` onwards, code comments for new work cite the
committed design document (`docs/superpowers/specs/…`) rather than a new §. Existing §
references stay exactly as they are; this is a rule for new work, not a migration.

## 9. Sequencing

1. **A1** — measure the sensor read. Cheapest possible outcome first.
2. **A2, A3** — demand-driven tier and the benchmark rows.
3. **B1, B2, B3** — the freeze, with B2 advisory until the tag.
4. **C1, C2** — the spec backlog.
5. **D** — the soak and the archive runs. This is wall-clock, not effort.
6. **Release** — CHANGELOG, README, checklist, tag.

The three features are built in a separate worktree during D's wall-clock time and merge
**after** the tag, so the CHANGELOG can state without qualification what 1.0.0 promised.

## 10. Definition of done

§23's list applies to every item here. On top of it, 1.0.0 is done when:

* the idle self-CPU p95 is under 2% on a recorded run, with the Battery-screen-open figure
  published beside it;
* a 12-hour soak exists for Linux and for macOS, each quotable with its workload;
* every published archive has been executed on its own architecture, or the exception is
  named in the CHANGELOG;
* the schema inventory test and the semver job are in CI, and the semver job is blocking;
* `docs/screenshots/` contains Linux frames;
* every claim in `README.md` is backed by a test or a recorded measurement — which is
  §23's `0.1.0` rule, restated because it is the one that keeps this project honest.

## 11. Risks and open questions

* **A1 may find nothing cheap**, leaving A2 to carry the budget alone. Acceptable: A2 is
  sufficient on the arithmetic, and A1 is bounded to a measurement.
* **The Battery-screen-open p95 will fail its budget.** By design, published, and argued
  in A3. If that argument is rejected on review, the fallback is a slower cadence while the
  screen is open (10 s) with the staleness age shown — worse ergonomics, cleaner number.
* **The soak may surface a real leak.** That is the point of running it. If it does, the
  finding becomes its own work item and the tag waits.
* **A Linux VM cannot validate the battery path**; only physical hardware with a battery
  can. If the physical machine is a desktop, that row stays fixture-tested and the
  CHANGELOG says so.
* **`cargo-semver-checks` may flag pre-existing API shapes** the moment it goes blocking.
  Better discovered while it is advisory, which is why it lands before the tag rather
  than after.
